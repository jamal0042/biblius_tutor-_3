# BIBLIUS — AGENT DEVELOPMENT CHARTER

Biblius is a professional university library management platform and digital library.

This file defines how AI coding agents must work inside the Biblius repository.

These rules are mandatory.

The goal is not only to produce working code.

The goal is to build a platform that is:

- professional
- modern
- elegant
- intuitive
- accessible
- responsive
- secure
- performant
- maintainable
- scalable
- consistent
- pleasant to use
- appropriate for a university library environment


# 0. CRITICAL RULE — THINK BEFORE MODIFYING

## NEVER MODIFY THE PROJECT IMMEDIATELY FOR A NON-TRIVIAL TASK

When a user requests a feature, modification, redesign, refactoring, bug fix, or architectural change, DO NOT immediately start editing files.

First understand the existing system.

The agent MUST follow this sequence:

    UNDERSTAND
        ↓
    INSPECT
        ↓
    ANALYZE
        ↓
    PLAN
        ↓
    IMPLEMENT
        ↓
    VERIFY
        ↓
    REVIEW

Do not skip directly from:

    USER REQUEST → CODE

The correct workflow is:

    USER REQUEST
          ↓
    UNDERSTAND THE INTENT
          ↓
    INSPECT EXISTING CODE
          ↓
    IDENTIFY EXISTING FEATURES
          ↓
    IDENTIFY REUSABLE COMPONENTS
          ↓
    IDENTIFY DEPENDENCIES
          ↓
    ANALYZE DATABASE
          ↓
    ANALYZE SECURITY
          ↓
    ANALYZE UX/UI
          ↓
    CREATE IMPLEMENTATION PLAN
          ↓
    IMPLEMENT CAREFULLY
          ↓
    TEST
          ↓
    REVIEW
          ↓
    COMPLETE

## During analysis, do not modify files

For complex tasks, analysis should be read-only.

The agent should inspect:

- pages
- layouts
- components
- hooks
- utilities
- types
- Supabase queries
- database migrations
- authentication
- authorization
- existing design patterns
- existing forms
- existing tables
- existing dialogs
- existing loading states
- existing error handling
- responsive behavior
- theme implementation

Only after understanding the impact should implementation begin.

## Before editing

The agent should be able to answer:

1. What already exists?
2. What exactly is missing?
3. Why does it need to change?
4. Which files are affected?
5. Which files should NOT be affected?
6. Can existing components be reused?
7. Does the database need to change?
8. Does authentication or authorization need to change?
9. Are there security implications?
10. Are there responsive implications?
11. Are there dark/light mode implications?
12. Could this break existing functionality?
13. What is the safest implementation strategy?

If these questions cannot reasonably be answered, continue inspecting before coding.


# 1. DO NOT BLINDLY REWRITE EXISTING CODE

Never rewrite an entire file simply because a new implementation appears cleaner.

Prefer:

- incremental changes
- targeted modifications
- component extraction
- reuse
- refactoring only when justified

Preserve existing functionality unless the user explicitly requests its removal.

Do not replace working architecture without understanding why it exists.

Do not "clean up" unrelated code while implementing a feature.

Do not modify unrelated files merely because they could be improved.


# 2. BIBLIUS IS A PRODUCT, NOT A COLLECTION OF PAGES

Think of Biblius as a complete digital product.

Every page, component, workflow, form, table, dialog, notification and interaction must feel like part of the same product.

A new feature must not look like it came from another application.

Maintain consistency in:

- visual language
- spacing
- typography
- colors
- buttons
- forms
- tables
- dialogs
- navigation
- icons
- notifications
- loading states
- empty states
- error states
- responsive behavior
- dark/light mode


# 3. PRODUCT QUALITY STANDARD

Every implementation should be evaluated from five perspectives:

## UX

Would a librarian, student, teacher, researcher or administrator understand this immediately?

## UI

Does it visually belong to Biblius?

## Engineering

Is the implementation maintainable and technically sound?

## Security

Can the user bypass the intended permission system from the browser?

## Data

Can the implementation corrupt, duplicate or lose library information?

A feature is not complete if only the code works.


# 4. USER-CENTERED DESIGN

Always think from the user's perspective.

The interface should make it obvious:

- where the user is
- what information they are seeing
- what actions are available
- what action is recommended
- what happened after an action
- whether an operation succeeded
- what went wrong
- what to do next

Never force users to understand internal technical concepts.

Avoid technical language in user-facing interfaces.


# 5. USER ROLES

Biblius may serve different users.

Examples include:

- administrator
- librarian/staff
- student
- teacher
- researcher
- other authorized members

Do not assume that every user has the same permissions.

Always respect the existing role system.

Never rely only on hiding a button to enforce permissions.

Permissions must be enforced at the appropriate backend/database/server level.


# 6. VISUAL IDENTITY

Biblius uses a strong:

- Blue

Blue communicates:

- trust
- technology

- success

Library users frequently work with large datasets.

Search interfaces should be:

- obvious
- fast
- forgiving
- responsive
- easy to clear

Filters should be understandable.

Do not make users configure complex technical filters unless the use case requires it.

Preserve useful filters during navigation when appropriate.


# 15. LOADING STATES

Never show an apparently broken blank interface while data is loading.

Use appropriate:

- skeletons
- loading indicators
- disabled actions
- progress indicators

Loading states should resemble the final UI whenever possible.


# 16. EMPTY STATES

An empty state is not necessarily an error.

Explain:

1. What is empty?
2. Why it may be empty?
3. What the user can do next?

Example:

"No document trouvé"

"Votre bibliothèque ne contient encore aucun document correspondant à votre recherche."

"Ajouter un document"


# 17. ERROR STATES

Errors must be understandable by non-technical users.

Never expose:

- SQL errors
- stack traces
- internal database details
- internal Supabase errors
- implementation details
- secrets

Translate technical failures into useful French messages.

Technical details may be logged appropriately on the server.


# 18. USER FEEDBACK

Every important action must provide feedback.

Example:

CREATE:

        ↓
    loading

        ↓
    success / error

# 19. DESTRUCTIVE ACTIONS

For destructive actions:

- clearly identify the consequence
- require confirmation when appropriate
- verify authorization
- prevent accidental double submission
- provide feedback

Never silently delete important library data.

Consider whether historical records should be preserved.

# 26. DATA LAYER — CRITICAL

The database is:

    Supabase PostgreSQL

Schema management:

    supabase/migrations/

Naming convention:

    snake_case

Examples:

- members
- documents
- auteurs

- exemplaires
- locations
- prets
- retours

Database changes MUST normally be implemented through SQL migrations.

Never make uncontrolled production schema changes from application code.


# 27. DATABASE CHANGE PROCESS

When changing the database:

1. Inspect the current schema.
2. Identify existing relationships.
3. Identify constraints.
4. Identify RLS policies.
5. Check existing migrations.
6. Determine whether a migration is necessary.
7. Create a new migration.
8. Preserve existing data.
9. Add constraints where appropriate.
10. Add indexes where justified.
11. Review RLS implications.
12. Verify application compatibility.

Never modify a database table blindly.


# 28. PRISMA

Prisma is NOT used by the application.

Do not:

- create Prisma models
- introduce Prisma queries
- run Prisma migrations
- replace Supabase with Prisma

The existing Prisma material is legacy/vestigial.

Do not introduce Prisma unless the project architecture is explicitly changed by the user.


# 29. SUPABASE CLIENT ARCHITECTURE

Browser/client operations use:

    @/lib/supabase/client

Server operations use:

    @/lib/supabase/server

Reuse existing:

- createClient()
- createServerSupabaseClient()
- getCurrentMember()

Do not create duplicate Supabase clients unnecessarily.


# 30. SUPABASE RELATIONS

Supabase embedded relations may return:

    T | T[] | null

Never assume that an embedded relation always has a single object or always has an array.

Never blindly write:

    row.documents[0]

unless the returned data has explicitly been normalized.

Reuse existing:

    MaybeArray<T>

and:

    toSingle()

patterns used throughout:

- src/app/admin/*
- src/app/dashboard/*


# 31. SECURITY — FIRST CLASS REQUIREMENT

Security must be considered during implementation, not after implementation.

Never:

- expose service-role keys in browser code
- trust client-side authorization
- bypass RLS
- expose sensitive data through uncontrolled queries
- store sensitive tokens unnecessarily
- assume hidden UI equals security

Always consider:

- authentication
- authorization
- RLS
- server-side validation
- input validation
- ownership
- role permissions
- data exposure
- auditability


# 32. SERVICE ROLE KEY

The Supabase service-role key is highly sensitive.

Never:

- place it in client components
- expose it through public environment variables
- send it to the browser
- log it
- commit it

Server-only privileged operations must remain server-side.


# 33. AUTHORIZATION

For administrative or privileged operations:

1. Verify authentication.
2. Verify role.
3. Verify permissions.
4. Validate input.
5. Validate target resource/context.
6. Perform operation securely.
7. Return only necessary information.

Never trust:

- role values sent by the client
- IDs supplied by the browser
- hidden buttons
- disabled buttons
- client-side redirects

# 38. CLASSIFICATION & DEWEY

Classification must be treated separately from document type.

A document can have:

- document type
- subject/domain
- Dewey classification
- cote
- physical location

Do not confuse these concepts.

If Dewey classification is used:

- preserve hierarchy
- preserve parent/child relationships
- support professional classification workflows
- allow authorized/manual classification
- allow AI-assisted suggestions only as suggestions
- require human validation where appropriate

Do not claim to have a complete proprietary Dewey dataset unless one is actually available and authorized for use.


# 39. AI FEATURES

AI must assist users, not silently make irreversible decisions.

AI may be used for:

- classification suggestions
- metadata suggestions
- duplicate detection
- summaries
- recommendations
- search assistance
- document analysis

AI-generated information should be clearly distinguishable from validated library data.

Critical metadata should be reviewable before being committed.

Never allow AI to silently modify critical library records without appropriate validation.


# 40. PERFORMANCE

Consider performance for thousands or millions of records.

Avoid:

- unnecessary client-side fetching
- repeated database requests
- duplicated queries
- unnecessary re-renders
- huge client bundles
- unnecessary dependencies
- unoptimized images

Use pagination for large datasets.

Use appropriate database indexes.

Do not load entire library datasets into the browser unnecessarily.


# 41. SERVER VS CLIENT COMPONENTS

Do not turn entire pages into client components without a reason.

Prefer server components when appropriate.

Use client components when interaction/state/browser APIs require them.

Consider:

- security
- performance
- data fetching
- bundle size
- hydration


# 42. REUSABILITY

Before adding code:

Search the repository.

If a similar implementation exists:

- reuse it
- extract it
- extend it

Do not duplicate logic.

If multiple pages contain the same logic, consider a shared abstraction when appropriate.


# 43. DEPENDENCIES

Do not install a package simply because it makes one task easier.

Before installing a dependency:

1. Search existing dependencies.
2. Check whether the functionality already exists.
3. Consider bundle size.
4. Consider maintenance.
5. Consider security.
6. Consider long-term value.

Prefer the existing stack.


# 44. TYPESCRIPT

Do not immediately patch the first suspicious line.

1. symptoms
2. reproduction
3. root cause
4. affected components

- reuse it
- extend it
- refactor it only if necessary

Avoid duplicate abstractions.


# 69. WHEN THE USER ASKS FOR DATABASE CHANGES

Do not immediately edit application code.

First inspect:

- migrations
- related tables
- foreign keys
- indexes
- RLS
- application queries
- types

Then:

    schema analysis
        ↓
    migration
        ↓
    application update
        ↓
    verification


# 70. WHEN THE USER ASKS FOR SECURITY CHANGES

Security changes require extra caution.

Before implementation:

- inspect authentication
- inspect authorization
- inspect RLS
- inspect server/client boundaries
- inspect exposed APIs
- inspect environment variables

Never solve a security problem solely through UI.


# 71. WHEN THE USER ASKS FOR PERFORMANCE IMPROVEMENTS

First measure or identify the bottleneck.

Do not introduce optimizations without understanding the problem.

Consider:

- database queries
- indexes
- network requests
- rendering
- hydration
- client bundles
- images
- caching
- pagination

Prefer meaningful optimization over premature optimization.


# 72. WHEN THE USER ASKS FOR "THE BEST" SOLUTION

Do not interpret "best" as:

- most complex
- most modern
- most dependencies
- most abstractions

Interpret "best" as:

- appropriate
- maintainable
- secure
- scalable
- performant
- consistent
- understandable
- aligned with Biblius


# 73. PRODUCT MATURITY

Biblius should evolve toward a production-quality platform.

Prioritize:

1. correctness
2. security
3. usability
4. consistency
5. maintainability
6. performance
7. scalability
8. visual polish

Do not sacrifice security or correctness for visual novelty.


# 74. GOLDEN RULE

When uncertain, choose the solution that:

- preserves existing functionality
- minimizes unnecessary changes
- improves user experience
- respects the Biblius design system
- respects the existing architecture
- protects user data
- remains maintainable
- can scale
- can be tested
- is understandable to another developer

Do not choose the solution merely because it is faster to code.


# 75. FINAL AGENT CHECKLIST

Before declaring a task complete, ask:

### Understanding

- Did I understand the existing implementation?

### Architecture

- Did I respect the existing architecture?

### Reuse

- Did I reuse existing components and utilities?

### UX

- Is the feature intuitive?

### UI

- Does it look like Biblius?

### Brand

- Did I preserve Blue + Gold?

### Responsive

- Does it work on small and large screens?

### Theme

- Does it work in dark and light mode?

### Accessibility

- Can users interact with it accessibly?

### Security

- Are permissions enforced properly?

### Database

- Is data integrity preserved?

### Performance

- Is the implementation efficient?

### Code quality

- Is the code maintainable?

### Regression

- Could existing features have been broken?

### Verification

- Did lint pass?
- Did TypeScript pass?
- Did build pass when appropriate?

If any important answer is "no", the task is not finished.
